## Stochastic simulation (`project/stochastic/`)
- [ ] `lambda_risk` (Q-measure market price of risk) is deliberately left at its zero default rather than calibrated. Two blockers, documented in `hjm_model.py::_evolve_pcs`: (1) this project only has spot Treasury yields, not derivative prices, so there's no clean data to calibrate a real price of risk against without building an empirical term-premium estimator (e.g. Fama-Bliss-style excess-return regressions); (2) it's unclear whether `lambda_risk` is even a free parameter in this construction, or redundant with the `_hjm_drift` no-arbitrage adjustment `simulate()` already applies directly to the forward curve under Q -- that relationship hasn't been derived. Needs a methodology decision before any calibration is trustworthy.
- [ ] `HJMModel.simulate_with_parameter_uncertainty` isn't wired into the walk-forward backtest (`project/stochastic/backtest.py`) -- each origin refits a plug-in point-estimate OU only. Worth adding once the per-origin cost (already dominated by one `differential_evolution` call per origin) is worth multiplying by a posterior draw count.
- [ ] Even after fixing the initial-state bug below, a smaller, genuine residual remained in the 2022-23 hiking cycle (validation region): the simulated 90% band covered the realized rate only 52-76% of the time there on this project's original 2018-2026 sample, worst at short maturities. That's the fastest, most aggressively front-loaded tightening cycle in the sample, and unlike the bug below, this looked like an actual P-measure limitation: OU `theta` is a trailing-history average with no mechanism for "policy is currently moving hard in one direction." Extending the training data back to 2001 (see README's "The Data") moved this substantially without anyone targeting it -- validation-region coverage is now 74-87%, still short of 90% but meaningfully closer. Plausibly because `theta` now has more regime diversity to average over, but that mechanism hasn't actually been isolated from "just more rows in general" -- untried: rerun with the extended data but capped to a similarly-short recent window, to separate "more regimes" from "more data" as the explanation. Other candidate fixes, still untried: a shorter or exponentially-weighted training window so `theta` adapts faster; conditioning the simulated drift on the FOMC's own forward path (a form of the `lambda_risk`/Q-measure question above).
- [ ] Comparing against a naive random-walk baseline (`run_backtest`'s `naive_forecast` columns, added alongside the fix above) surfaced a further finding that the later data extension partly reversed: on the original 2018-2026 sample, `skill_vs_naive` on the held-out test region was negative at most horizons and most maturities past the very short end -- the model's point forecast rarely beat "assume nothing changes." On the extended 2001-2026 sample, `skill_vs_naive` is now positive at the 63/126/252-day horizons and negative only at 21 days. Not diagnosed further than "the extended history changed the calibration enough to flip the sign at most horizons" -- worth revisiting once the mechanism behind the coverage-gap narrowing above is understood, since they may share a cause.
- [ ] Adding a second baseline (`_fit_ml_baseline_at_origin`, a `RandomForestRegressor` fit walk-forward the same way) refined the naive-baseline finding rather than confirming it: `skill_vs_ml`, pooled across tenors, is *positive* at every horizon tested on both samples (now +22% to +42%) -- the HJM model beats the ML baseline on average. Combined with the naive result above, the RMSE ranking is no longer horizon-independent: naive still wins at the shortest (21-day) horizon, but the HJM model wins at 63 days and beyond, with random forest last throughout. Only one tabular ML baseline was tried, with one feature set (lagged levels across all tenors) and default-ish hyperparameters -- a more carefully feature-engineered or tuned ML model might close that gap or reverse it, so "beats a standard ML baseline" shouldn't be read as "beats what ML can do here."
- [ ] New finding from the extended sample, not present on the original 2018-2026 one: test-region coverage is now *significantly above* the 90% nominal target at every horizon (100%, Wilson CI never dipping below 98%) -- not just numerically high, but a band that looks wider than it needs to be to hit 90%. A safer failure mode than the original under-coverage bug, but still a real miscalibration worth understanding rather than treating "100% coverage" as an unqualified win. Untried: check whether OU `sigma` for the test-region-relevant factors came out larger on the extended sample than the original one (would directly explain a wider band); if so, decide whether that's the calibration correctly reflecting more historical volatility, or overfitting to regimes (2008, COVID) the 2024-2026 test region doesn't resemble.
- [ ] `_wilson_interval` (the coverage confidence interval) treats each origin as an independent Bernoulli trial. Origins from overlapping windows (a 21-day step against a 63+ day horizon) aren't independent, so the reported interval is narrower than the true uncertainty. A block-bootstrap or Newey-West-style correction would be the honest fix; not implemented.

## Testing & tooling
- [ ] `.github/workflows/refresh-data.yml` now runs `scripts/refresh_treasury_data.py` on a schedule and fails loudly on a bad fetch or a data-quality flag -- but it deliberately does not commit refreshed data back to `main`. Doing that for real needs a DVC remote (`.dvc/config` is currently empty, no S3/GCS/other store configured) and a decision about who's allowed to have a bot auto-commit to main -- both left to whoever deploys this rather than decided silently in a workflow file.
- [ ] The `Dockerfile` was written against this project's exact known-working dependency versions and standard practice, but hasn't actually been build-tested -- the environment this was authored in has no Docker daemon available. Someone with Docker installed should run `docker build -t hjm-libor-model .` and `docker run --rm hjm-libor-model` once before relying on it; QuantLib's compiled bindings are the most likely thing to need a fix (a missing prebuilt wheel for some platform would force a from-source build, which `build-essential` is included to support but hasn't been exercised).
- [ ] `.github/workflows/tests.yml` runs the full test suite (including `slow`-marked ones) on every push/PR to `main`, on Python 3.9 to match the Dockerfile and this project's actual development environment -- deliberately not 3.11 like `refresh-data.yml`, since that workflow never imports `pymc`/`arviz` and so is no evidence they install cleanly under a newer Python. This has only been reasoned through and checked against the local venv, not confirmed by watching an actual run go green on GitHub (no `gh` CLI or other way to check Actions runs was available in the environment this was authored in) -- worth glancing at the Actions tab after this lands on `main` to confirm the first run passes, and at the README badge going green.
- [ ] `Requirements.txt` pins no versions at all (bare package names) -- fine for a single, already-working local venv, but it means `tests.yml`, `refresh-data.yml`, and the Dockerfile can each silently resolve different dependency versions from each other and from what's actually been tested, especially for the `pymc`/`arviz`/`numpy` stack that's already broken once from a version mismatch (see README's "A Number Isn't the Same as Knowing the Number" history). Pinning exact versions (a `requirements.lock` or switching to a tool that generates one) would make all three actually reproducible against each other instead of each independently hoping `pip install` resolves the same way.
